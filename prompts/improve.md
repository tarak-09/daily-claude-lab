## How to work

- Read the code you are changing, and its tests, before changing anything.
  Follow the project's existing structure and conventions, and do not
  restructure what you are not fixing.
- For a bug: first write a test that fails because of the bug, then fix the
  bug, then show that the test passes.
- Every behaviour you change gets a test. Tests must be deterministic: no
  sleep-based synchronisation, no dependence on network access or wall-clock
  timing.
- Keep the diff focused: well under ${MAX_CHANGED_LINES} changed lines,
  lockfiles excluded.
- If you add or change dependencies, update the lockfile with the project's
  own tool (for example `uv lock` or `npm install`) and keep it in the change.
- Update the README only where behaviour or usage changed, and never document
  something you did not implement.
- ${CI_RULE}
- Do not add or change a LICENSE.
- Do not add Dependabot, Renovate, or any automation that commits or opens
  pull requests under its own identity: the owner must stay the only
  contributor.
- Do not run `git commit` or `git push`, and do not change git configuration.
  The workflow commits your working tree as a single commit.

The workflow refuses to publish the change if any of these is true, so avoid
them: build output, dependency directories, caches, runtime databases or logs
in the diff; a credential-shaped string in an added line (if you need
secret-shaped test fixtures, assemble them at runtime from pieces); a git
submodule; more than ${MAX_CHANGED_LINES} changed lines.

## Verify

Install the dependencies, run the FULL test suite, and exercise the changed
behaviour for real by running the program. Fix whatever breaks. Before anything
is published, the workflow re-runs your test command on the exact commit and
refuses to publish if it fails.

## Output files

1. `${OUT_DIR}/report.json`: exactly one JSON object with these keys:
   - "summary": 2 or 3 sentences on what changed and why
   - "tests_command": one shell command, run from the repository root, that
     runs the whole test suite with the dependencies you installed, e.g.
     `uv run pytest -q` or `npm test`
   - "tests_ran": true or false
   - "tests_passed": true or false
   - "verified": what you executed to prove the change works, with the key
     output
   - "notes": risks, follow-ups, anything a reviewer should know
2. `${OUT_DIR}/pr-body.md`: the pull request description, written for a human
   reviewer, in Markdown, with these sections: Problem (with the evidence),
   Change, How it was verified (commands and their real output), Risks and
   follow-ups. No sign-off, co-author or "generated by" lines. Do not
   @-mention anyone (write package scopes such as `@types/node` in
   backticks), and do not write closing keywords such as "fixes #3": the
   workflow links the issue itself.

Report honestly. If the tests fail, say so: the workflow will not publish, and
that is the correct outcome.
