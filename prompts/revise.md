## What to do

- Owner feedback: address every item. Where an item is a question, or you are
  confident the requested change would be wrong, do not change code for it:

- Failing checks: reproduce the failure locally with the same commands the CI
  workflow runs, find the root cause, and fix it. Never weaken, skip or delete
  tests or checks to make them pass, and do not loosen lint or type rules
  unless the rule itself is the defect.

- The standards of the original change still apply: tests for changed
  behaviour, the lockfile updated with any dependency change, nothing
  generated committed, no LICENSE changes. ${CI_RULE}
- Do not run `git commit` or `git push`, and do not change git configuration.
  The workflow commits your working tree as one new commit on this branch.

directories, caches, runtime databases or logs, a credential-shaped string or
a git submodule, or if it exceeds ${MAX_CHANGED_LINES} changed lines.

## Output files

1. `${OUT_DIR}/report.json`: exactly one JSON object with these keys:
   - "commit_title": a one-line commit subject, imperative mood, at most 72
     characters
   - "summary": 2 or 3 sentences on what changed

     runs the whole test suite

   - "tests_passed": true or false
